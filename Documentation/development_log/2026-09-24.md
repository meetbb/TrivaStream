# 2026-09-24

## Changed

- `LibraryView` replaced its `List` with a `LazyVGrid` of card cells (waveform
  thumbnail, title, artist), matching ADR-004's "no structure without a
  concrete trigger" — this was a presentation-layer change, no new
  architectural layer.
- Freesound.org is now TrivaStream's sole content source, on your explicit
  instruction to remove the bundled catalog entirely:
  - `BundledContentRepository`, `BundledContentRepositoryTests`,
    `catalog.json`, `CompositeContentRepository`, and
    `CompositeContentRepositoryTests` all deleted.
  - `FreesoundContentRepository.fetchCatalog()` (previously a no-op) now
    calls the same authenticated `/apiv2/search/text/` endpoint as
    `search(query:)`, with `query=""`. Both share one `performSearch`
    helper. No custom `sort` yet — Freesound's own default ordering, by
    your decision to handle sorting/ordering as separate follow-up work.
  - `MediaCatalogItem` gained `thumbnailURL: URL?`, populated from
    Freesound's `images.waveform_m`.
  - `TrivaStreamApp` now injects `FreesoundContentRepository` directly as
    the sole `ContentRepository` (no more Composite/Bundled wiring).
- `LibraryView` error handling: a launch-load failure (no items at all)
  replaces the grid with a centered `ContentUnavailableView` and hides the
  search bar; a search-time failure (items already loaded) keeps the grid
  and search bar and shows an inline error instead.

## Bug found and fixed (same day)

- Reported symptom: thumbnails visibly "redisplayed" when returning from
  `PlayerView` to the Library grid. Investigated with temporary
  instrumentation (call counters exposed via hidden, accessibility-tagged
  labels, read by a throwaway UI test — `print()`/log-stream capture proved
  unworkable in this sandbox, since `xcodebuild test`'s managed simulator is
  torn down before any log can be collected).
  - Confirmed `loadCatalog()` genuinely re-runs when returning from
    `PlayerView` (call count 1 → 2) — contradicts the usual assumption that
    a `NavigationStack`'s root content is untouched by push/pop.
  - Root cause of the *visible rebuild*: `MediaCatalogItem.id` defaulted to
    a fresh random `UUID()` on every parse, so even identical reloaded
    content got entirely new SwiftUI identities, forcing `ForEach` to
    destroy and recreate every cell and thumbnail.
  - Fix (scope explicitly limited to this by your choice): `id` now comes
    from Freesound's own stable sound `id` field instead of a random UUID.
    Verified via a new unit test and by the diagnostic rebuild count
    dropping from 3x to 2x per reload cycle.
  - Not fixed (deferred, also by your choice): the `loadCatalog()` rerun
    itself, and the fact that even with stable IDs the reload still rebuilds
    the grid once — because Freesound's empty-query response isn't
    returning the same set of items across calls (see Known limitations).
  - All temporary debug counters/overlay and the throwaway UI test were
    removed once the diagnosis and fix were verified.
- Separately, `TrivaStreamApp` was constructing `LibraryViewModel` inline
  inside the `WindowGroup` scene-builder closure instead of as a stored
  property — a direct violation of ADR-002/003's "created once at the
  composition root, never inside a View or scene builder closure" rule
  (pre-existing, not introduced today; `playerViewModel` already followed
  the rule correctly). Fixed: `libraryViewModel` is now a stored `let`,
  assigned once in `TrivaStreamApp.init()`.

## Known limitations

- **`AsyncImage` in `LibraryGridCell` does its own networking directly from
  the View layer**, bypassing `ContentRepository`. CLAUDE.md's architecture
  rule says "the UI must not directly contain networking... logic." This is
  standard, idiomatic SwiftUI (most codebases load incidental images this
  way, not through a repository), so it's arguably not a true boundary
  violation — but a strict reading of the project's own rule does flag it,
  so it's left here as an open item rather than silently decided either way.
  **Deliberately left as-is today** — flagged for you to work on the
  networking layer yourself tomorrow.
- `fetchCatalog()` queries Freesound with an empty `query` and no `sort`;
  the API's ordering for that case does not appear to be deterministic
  across repeated calls (see the bug investigation above — this is what
  caused the grid to still rebuild once per reload even after the stable-ID
  fix). Ties directly into the sort/ordering work already deferred as
  separate follow-up.
- `loadCatalog()` re-running when returning from `PlayerView` is confirmed
  but not addressed — only the *symptom* (unnecessary full grid/thumbnail
  rebuild) was fixed via stable IDs, not the redundant network call itself.
- No retry/backoff on Freesound rate limits or transient failures (carried
  over from 2026-09-23).
