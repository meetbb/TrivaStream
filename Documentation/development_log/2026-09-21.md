# 2026-09-21

## Changed

- Added a seek/progress scrubber to the player: a `Slider` with elapsed and
  remaining time labels. `PlayerViewModel` gained `currentTime`, `duration`,
  `scrubPosition`, `displayedTime`, `isSeekable`, `scrub(to:)`, `commitScrub()`
  and `trackProgress()`. `AudioPlayer` exposes no time stream, so progress is
  polled every 0.5s.
- Polling is owned by the screen: `PlayerView` runs
  `.task { await viewModel.trackProgress() }`, so leaving the screen cancels it.
  Nothing polls while the player is not on screen.
- The slider is enabled only in `.idle`, `.playing` and `.paused` with a known
  duration. It is disabled while `.loading` and in `.error`.
- After playback ends the scrubber stays visible with the thumb at 0:00, and a
  seek from there lands `.paused`.
- Found a bug on the simulator: seeking while playing left the engine stuck in
  `.buffering`, so the UI stayed on the spinner with the slider disabled.
  Reproduced with a temporary UI test and the raw `states` log (last emitted
  state was `.buffering`). Root cause is in AudioStreamKit. It was fixed there
  and closed as an issue, and the seek flow was re-verified on the simulator.
- Fixes from a hostile self-review:
  - `PlayerViewModel` is now created once in `TrivaStreamApp`, next to the
    player, instead of inside the `WindowGroup` closure.
  - Its `states` observation `Task` is stored and cancelled in `deinit`.
  - `select(_:)` is idempotent for the active item, keyed by `url`, because
    `PlayerView` calls it on every appearance. An ended or failed item restarts.
  - `scrub(to:)` is ignored when not seekable and is clamped to the track
    length. The begin/scrub/end protocol was replaced by `scrubPosition` plus
    `commitScrub()`, and the thumb is released only after `currentTime` has
    caught up with the seek.
  - `.error` resets `currentTime` and `duration`. A progress read is dropped if
    a different item was selected while it was in flight.
- Tests:
  - `PlayerViewModelTests` (19 tests) drives a real `AudioPlayer` against
    `LoopbackMediaServer`, a small local HTTP server with `Range` support that
    serves generated silent WAV files.
  - `PlaybackFlowUITests` (2 tests): seek/pause/resume/switch-track flow, and
    playback continuing after the app is sent to the background.
  - Each fix was checked by deliberately breaking it and confirming a test fails.

## Decisions

- Polling, not observing: the pull API is deliberate in AudioStreamKit.
- Spinner flashes on a seek (seek re-buffers through `.loading`). Accepted for
  v1, revisit later.
- The scrubber stays visible after `.ended`, reset to the idle look.
- Selecting the active item does nothing unless it is ended or failed.
- No test seam or wrapper for `AudioPlayer` in TrivaStream (ADR-001). Tests use
  a real player and a loopback server. AudioPlayer's own behavior is tested in
  AudioStreamKit.
- The AudioStreamKit bug was fixed in AudioStreamKit, not worked around in the
  app.
- Review finding "`currentTime` and `duration` can be inconsistent" was
  declined: both are written back to back on the main actor and duration is
  constant per item.

## Known limitations

- `PlaybackUIState` folds `.loading`, `.buffering` and `.stalled` into
  `.loading`, so the UI cannot tell initial load, seek re-buffer and network
  stall apart. Deferred.
- `.idle` covers "nothing selected", "ended" and any future stopped state;
  `isSeekable` relies on the duration being non-nil to tell them apart.
  Deferred.
- `select(_:)` still has no guard against overlapping calls, and
  `togglePlayPause` still calls `play()` during `.loading` with a play icon.
  The guard task is separate. There is also a narrow window where a second
  `select` of the same item slips through before the stream has emitted
  `.loading`.
- Progress is read every 0.5s, so the bar moves in steps and the elapsed label
  can lag by up to that.
- While the screen is visible and paused, the loop still reads every 0.5s.
- Not covered by automated tests: a stall mid-drag clearing `scrubPosition`,
  the `.error` reset (the 404 test never reaches a non-zero position), the
  duplicate `.playing` event, and real interruptions or network drops.
- The background UI test passed on the simulator only. Simulators do not
  enforce background modes, and no `UIBackgroundModes` setting was found in the
  project file (a separate plist was not checked). Verify on a device.
- `LibraryViewModel` is still created inside the `WindowGroup` closure. It was
  not part of the review findings.
- Low-severity review findings (choppy progress, accessibility labels/values,
  view layout of the extension, seek tolerance and the unexplained
  74.7s-vs-~99s paused-seek reading in the UI run) were left for later.
- Test cost: unit tests use real time and the real default disk cache, and the
  UI tests need network, skipping when offline.
