# 2026-09-23

## Changed

- Added Freesound.org search, integrated behind the existing `ContentRepository`
  seam (ADR-003), triggered by ADR-004's trigger 1 (a second, real data
  source — search — now actually exists, not a hypothetical one):
  - `ContentRepository` gained `search(query:) async throws -> [MediaCatalogItem]`,
    default-implemented as `[]` so `BundledContentRepository` needed no changes.
  - `FreesoundContentRepository` (new): calls Freesound's
    `GET /apiv2/search/text/`, token auth via the `Authorization` header (not
    the URL), decodes results into `MediaCatalogItem` preferring the
    high-quality MP3 preview and falling back to low-quality, deduping by
    preview URL. `fetchCatalog()` is a no-op — Freesound has no catalog concept.
  - `CompositeContentRepository` (new): implements `ContentRepository` by
    routing `fetchCatalog()` to the bundled source and `search(query:)` to
    Freesound, so `LibraryViewModel` still depends on exactly one
    `ContentRepository`.
  - `LibraryViewModel` gained `searchText` and a 400ms-debounced `search()`
    (empty query restores the bundled catalog items).
  - `LibraryView` gained `.searchable(text:)` wired to `.task(id: searchText)`.
- Scope is deliberately preview-only: token/API-key auth, 128kbps MP3
  previews. No OAuth2 user login, no full-quality downloads.
- Secrets: `Secrets.xcconfig` (project root, gitignored;
  `Secrets.xcconfig.example` checked in as the template) holds
  `FREESOUND_API_KEY`, wired into the app target via `baseConfigurationReference`.
- Tests: `FreesoundContentRepositoryTests` (parsing + a stubbed `URLProtocol`
  network test, no live calls), `CompositeContentRepositoryTests`
  (delegation), and new `LibraryViewModelTests` cases for `search()`.

## Bug found and fixed (same day)

- After implementation, search silently returned nothing in the running app
  even though a direct `curl`/browser call to Freesound with the same key
  worked. Root cause: `INFOPLIST_KEY_FreesoundAPIKey`, set via
  `Secrets.xcconfig`, was silently dropped by Xcode's
  `GENERATE_INFOPLIST_FILE = YES` synthesis — that mechanism only recognizes
  a fixed, built-in allowlist of `INFOPLIST_KEY_*` settings (scene manifest,
  launch screen, orientations, etc.), not arbitrary custom keys. No error,
  no warning — `Bundle.main.object(forInfoDictionaryKey:)` just returned
  `nil`, so every request went out with an empty `Authorization: Token `
  header.
  - Confirmed by inspecting the actual built `Info.plist` with `PlistBuddy`
    rather than assuming the build setting worked.
  - Fix: added a small partial `Info.plist` (project root) containing just
    `FreesoundAPIKey = $(FREESOUND_API_KEY)`, referenced via `INFOPLIST_FILE`
    kept *alongside* `GENERATE_INFOPLIST_FILE = YES` — Xcode merges the two.
  - First attempt put that file inside `TrivaStream/`, a synchronized source
    group, which made Xcode also try to copy it as a bundle resource
    (`Multiple commands produce .../Info.plist`). Moved it to the project
    root, same as `Secrets.xcconfig`, which isn't part of any synchronized
    group.
  - Re-verified with `PlistBuddy` against the freshly built app and a full
    test run after the fix.

## Decisions

- Preview-only Freesound scope over full OAuth2 downloads — smaller surface
  area, matches "media player" scope, avoids a per-user auth flow and token
  refresh handling.
- Search added as a method on the existing `ContentRepository` rather than a
  separate `SearchRepository` protocol — keeps ADR-003's single seam intact;
  `CompositeContentRepository` handles the two-source wrinkle without a new
  abstraction layer.
- Search lives in the existing Library screen via SwiftUI `.searchable`,
  not a separate screen — smallest UI change, no new navigation structure.
- API key stored in a gitignored `Secrets.xcconfig`, not Keychain — standard
  build-time pattern for a client API key with no per-user configurability
  need.

## Known limitations

- No retry/backoff on Freesound rate limits or transient failures.
- Live UI flow (typing in the search field, playing a Freesound preview
  end-to-end) was not exercised in a simulator this session — verified via
  build + full unit test suite + direct `PlistBuddy` inspection of the
  built `Info.plist`, not a manual run.
- The Freesound API key used during development was pasted in plaintext in
  chat; low-stakes (preview-only token) but should be rotated from the
  Freesound account when convenient.
